# 24. System Design — Insurance Claims & Payment Processing Platform on Kafka

**Target:** Principal Software Engineer V — The Standard (IBTE)
**Duration:** Whiteboard / 90-second overview
**Domain-Specific System Design** — tailored for insurance claims, payments, and event-driven architecture.

---

## Question

**Interviewer:** "Design an event-driven insurance claims and payment processing platform. How do you handle schema evolution, ordering, idempotency, and audit compliance?"

---

## Answer

To build a high-throughput, compliant insurance claims and payment platform, I design an event-driven microservices architecture anchored on Apache Kafka and Spring Boot.

**1. Architecture & Ingestion Layer:**
Claims arrive via an API Gateway (Kong/Azure API Management) which enforces OAuth2/JWT authentication, rate limiting, and input validation. The `Claim Ingestion Service` validates the payload and writes the raw claim event to a partitioned Kafka topic (`claims.received`).

**2. Domain Microservices & Event Streams:**
Downstream microservices process the workflow asynchronously:
- `Claim Adjudication Service`: Consumes `claims.received`, runs business rules, and emits `claims.adjudicated`.
- `Payment Processing Service`: Consumes `claims.adjudicated`, integrates with banking gateways, and emits `payments.disbursed`.
- `Audit & Compliance Service`: Consumes all topics into immutable cloud storage (Azure Blob/S3) for HIPAA/financial compliance.

**3. Ensuring Data Integrity & Reliability:**
- **Schema Evolution:** We enforce Confluent Schema Registry with strict `BACKWARD_TRANSISTIONAL` compatibility using Avro/Protobuf. Breaking schema changes are blocked at CI/CD build time.
- **Partitioning & Ordering:** Topics are partitioned by `claim_id` or `policy_number`. All state changes for a single claim land on the same partition, guaranteeing strict sequential processing per claim.
- **Idempotency & Exactly-Once:** We implement the **Transactional Outbox Pattern** on producers to ensure database commits and Kafka publishes happen atomically. Consumers maintain idempotent consumer handlers using a Redis/DB deduplication key (`event_id`).
- **DLQ & Error Budget:** Malformed events are routed to a Dead Letter Queue (DLQ) with automated alert thresholds, while transient failures leverage Resilience4j retry exponential backoff.

This design delivers sub-second transaction routing, guaranteed audit trails, and seamless scale across millions of annual insurance policy claims.

## Technical Specifications Table

| Component | Choice | Reason / Mechanism |
|---|---|---|
| Ingestion | Kong / Azure APIM | Edge authentication, rate limiting, payload validation |
| Event Backbone | Kafka (3x replication) | Multi-partition, event immutability, high throughput |
| State Management | Transactional Outbox | Guarantees DB write + Event publish atomic atomicity |
| Schema Control | Schema Registry | Enforces Avro/Protobuf backward compatibility |
| Deduplication | Redis / DB Unique Index | Idempotent consumer key validation (`event_id`) |
| Audit Trail | S3 / Azure Blob sink | Write-Once-Read-Many (WORM) storage for compliance |

## Key Signals

- **Enterprise Governance:** Using Schema Registry and Outbox pattern shows production-grade event-driven design depth.
- **Compliance & Security:** Highlighting immutable audit logs (WORM) fits financial/insurance domain requirements (The Standard).
- **Resilience:** Clear strategy for DLQs, retries, and exactly-once processing guarantees.

## Question

**Interviewer:** "We use Apache Flink for real-time stream processing and stateful calculations. What is your experience with Flink or real-time stream processing engines?"

---

## Answer

My core streaming foundation is built on **Apache Kafka** and event-driven state processing—specifically event streaming architectures, sliding window aggregations, out-of-order event handling, and dead-letter queue mechanics in Spring Kafka.

While my production implementations have primarily leveraged Kafka Streams, Kafka Connect, and custom Spring Boot microservices for event processing, the underlying stateful stream processing concepts translate directly to Apache Flink:

- **State Management & Checkpointing:** Understanding how Flink manages stateful operators (RocksDB state backend) is directly parallel to how we handle local state stores in Kafka Streams with changelog topics.
- **Event Time vs. Processing Time:** In our subscriber notification and telemetry pipelines, handling late-arriving data using watermarks and windowing strategies (tumbling vs. sliding windows) is a core design requirement we've solved.
- **Exactly-Once Semantics (EOS):** I've implemented two-phase commit transaction boundaries across Kafka producers and database outboxes to guarantee idempotent end-to-end processing.

If a project at The Standard requires Flink specifically, I understand the core execution model (JobManager, TaskManager, state checkpointing, and dynamic scaling). Given my deep Java, Spring, and Kafka foundation, picking up Flink API syntax or deployment on Kubernetes (via Flink Kubernetes Operator) takes matter of days, not weeks.

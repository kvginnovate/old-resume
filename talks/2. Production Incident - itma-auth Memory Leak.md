# 2. Production Incident — itma-auth Memory Leak

**Target:** Principal Software Engineer V — The Standard (IBTE)
**Duration:** 85-95 seconds

---

## Question

**Interviewer:** "You mentioned 99.9 percent uptime on the platform. Tell me about a specific production incident — what went wrong, how you handled it, and what you changed afterward."

---

## Answer

Our itma auth service, which is the central authentication service handling all login and token validation, was OOM killing every 6 to 8 hours in production on Rancher. It was processing about 50,000 requests per minute, and every crash meant users couldn't log in. This was a P0.

The first sign was pods crash looping on Rancher. Auto restart masked the problem temporarily. GC logs showed the heap growing steadily with no recovery after garbage collection, which is a classic memory leak pattern.

To stop the bleeding, I doubled the heap and added a daily restart cron. It was ugly, but it bought us time to diagnose without more production outages.

For root cause, I set up JMeter with 500 concurrent virtual users hitting the token validation endpoint to match the same load as production. I ran it for 30 minutes, took a heap dump, and opened it in YourKit. The leak was a JWT public key cache. The service cached signing keys from the JWKS endpoint in a HashMap with zero eviction. Every time the identity provider rotated keys every 24 hours, the old keys accumulated. After 7 days, the cache had 14 stale entries holding references to large certificate objects, and the map grew unbounded until OOM.

The root cause wasn't the cache itself. It was no eviction policy and no load testing for memory stability.

I drove three changes. First, I fixed the code — replaced the raw HashMap with Guava Cache Builder with a max size of 50, a TTL of 6 hours, and LRU eviction. Keys are now auto evicted. Second, I added a memory stability test — a JMeter script that runs 30 minutes of peak load and asserts heap growth under 10 percent. It's now a CI/CD gate. If the heap grows, the build fails. Third, I created a cache checklist — every service on the team now must document eviction policy, max size, hit rate metric, and an alert when eviction count spikes. This caught similar issues in two other services within a month.

The result was zero recurrence of the same class of bug in 6 months, and the team adopted the cache checklist as standard practice.

## Follow-Up Questions

- **"What was the hardest part of the diagnosis?"** — Getting the right load profile. The leak only showed under sustained production-like concurrency. Low load tests passed. I had to match the exact production traffic pattern.
- **"How did you get other teams to adopt the cache checklist?"** — I didn't mandate it. I showed them the heap dump — two of their services had the same pattern. Once they saw the evidence, they asked for the checklist.
- **"What would you do differently now?"** — I'd add a JVM metric for cache size to production dashboards proactively. We caught this when it crashed. I'd rather catch it trending.

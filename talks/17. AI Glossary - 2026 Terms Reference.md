## Purpose

One-line definitions of the 2026 agentic-AI vocabulary. Use this to speak the current language fluently in interviews — and to avoid fumbling when an interviewer drops a term. Each item is grounded in 2026 primary sources: the Digital Applied 200-term and 60-term glossaries (both anchor every entry to specs, arXiv papers, or vendor docs), the AIE 2026 Q1 report, Anthropic engineering posts, and the MCP specification.

**Highest-value section: the disambiguation table at the bottom** — the eight term-pairs that derail architecture meetings. If you only memorize one part of this doc, memorize that.

## Core Agent Concepts

| Term | One-Line Definition |
|---|---|
| Agent | An entity that perceives an environment and acts on it to achieve goals (Russell & Norvig) — distinguishes agents from chatbots |
| Agent loop | The bounded perceive → think → act → observe cycle an agent runs until goal completion, budget exhaustion, or halt |
| Agentic AI / agentic coding | AI that plans, acts, and uses tools across multi-step tasks instead of answering one prompt |
| Subagents | Child agents spawned by a primary agent with their own context window and tool budget (Claude Code: one level deep only) |
| Scaffolding | The harness — prompts, tool wiring, control flow, memory glue — wrapped around a base model to make it an agent |
| Multi-agent orchestration | Coordinating several agents — role assignment, task decomposition, cross-agent messaging, conflict resolution |
| Agent harness | The runtime that gives an agent tools, memory, guardrails, and telemetry |
| Agent pools | Teams of specialized agents (implementer, reviewer, tester) dispatched per task type |
| BYOA | Bring Your Own Agent — orchestration layers that accept Claude Code, Codex, Gemini CLI, etc. |
| ACI | Agent-Computer Interface — the surface (tools/CLI) agents act through |
| Vibe coding | Karpathy's term for accepting AI-generated code without reading it line-by-line — the anti-pattern your spec-driven process answers |

## Agent Loops & Control Flow

| Term | One-Line Definition |
|---|---|
| ReAct | Reason + Act (Yao et al. 2022) — the pattern interleaving a "thought" trace with an "action" tool call; still the default loop in most production agents |
| Reflexion | ReAct + an explicit self-critique step per iteration (Shinn et al. 2023); cuts repeated failure modes on long-horizon tasks |
| Plan-and-execute | Two-phase loop: a planning model emits an ordered plan; a separate (often cheaper) execution model walks it step by step |
| Hierarchical / supervisor pattern | A supervisor model decomposes tasks and routes them to worker sub-agents, then aggregates results |
| Swarm pattern | Peer agents with no supervisor, coordinated by a shared message bus; scales wider, harder to observe |
| Fan-out / fan-in | Dispatching parallel sub-tasks across agents, then merging at a synchronization barrier — the MapReduce of agent frameworks |
| Step | One iteration of the agent loop — distinct from a turn (user exchange) or a tool call |
| Step budget | Maximum step count past which the loop terminates regardless of state (production agents typically run 10–50) |
| Halt condition | The explicit "done" signal (e.g., a final_answer tool call) that ends the loop before the budget |
| Re-anchor | A checkpoint where prior state is summarized and the loop restarts with that summary — prevents context-cache invalidation on long runs |
| Durable execution | A runtime pattern where workflows survive crashes and retries by checkpointing every step (Temporal, Inngest, Restate) — without it a task failing at step 47 restarts from zero |

## Planning & Reasoning

| Term | One-Line Definition |
|---|---|
| Chain-of-thought (CoT) | Prompting the model to produce an explicit reasoning trace before the final answer (Wei et al. 2022) |
| Tree-of-thought (ToT) | Exploring multiple branching reasoning paths and selecting the best (Yao et al. 2023) — for problems with several valid solution paths |
| Self-consistency | Sampling N independent CoT traces and taking the majority answer — robust at N× token cost |
| Reasoning effort / thinking budget | A first-class model parameter (Claude extended_thinking, OpenAI reasoning_effort) controlling how many internal reasoning tokens are spent before answering |
| Test-time compute | Spending more inference-time compute (more reasoning tokens, more samples) to improve quality without retraining — the 2025-26 frontier scaling axis |
| Plan | An ordered, structured sequence of steps emitted by a planning model — data; the agent loop is the runtime that executes it |
| Subgoal | An intermediate target from decomposing the user goal — the unit of work delegated to workers in hierarchical topologies |
| Scratchpad | An ephemeral in-context working area for intermediate calculations or notes — consumed by the next model call, not persisted |
| Verifier | A separate model call (or rule) that checks a candidate answer for correctness or policy compliance — emit, verify, regenerate on failure |
| LLM-as-judge | Using an LLM to grade outputs against a rubric — cheap to scale, has known biases (length, recency, self-preference), must be calibrated against human grades |

## Memory & Context

| Term | One-Line Definition |
|---|---|
| Context window | The maximum token count a model can attend to in a single call — the operative constraint for long-running sessions |
| Context engineering | Designing what loads into the context window — system prompts, retrieved chunks, tool definitions, memory; the 2026 successor discipline to prompt engineering |
| Context lifecycle (CDLC) | Context creation → loading → use → cleanup, versioned and auditable |
| Context rot / contamination | Degradation when agents carry stale or polluted context |
| Context compression / compaction | Summarizing older context to fit the window |
| Retrieval budgeting | Deciding what to load into context vs. leave out |
| Memory tiering | Short-term working context vs. persistent memory (knowledgebase, shared, session) |
| Working memory | The portion of context devoted to transient task state — calculations, tool results, scratchpad |
| Short-term memory | Information held within the active context window; gone when the loop ends unless persisted |
| Long-term memory | Information persisted outside the context window, retrieved on demand |
| Episodic memory | Records of past interactions indexed by event — one row per session/task (Park et al. 2023, Generative Agents) |
| Semantic memory | Structured facts extracted from interactions — preferences, contract terms; stable across sessions |
| Procedural memory | Compiled "how-to" knowledge — playbooks, learned workflows, frozen prompt templates |
| Memory write / recall | Explicit persistence of facts into long-term memory (per-turn, session-end, or tool-call triggers) and retrieval back into context (vector, keyword, or graph) |
| State | The current snapshot of intermediate values in the orchestrator runtime — distinct from memory (persisted) and context (rendered to model) |
| RAG | Retrieval-Augmented Generation — generating conditioned on dynamically retrieved external context (Lewis et al. 2020) |
| Retrieval over context stuffing | Pulling the right knowledge on demand instead of cramming everything in |
| Embeddings | Dense numerical vectors representing the semantic meaning of text/code |
| Vector search | Similarity lookup over a database of embeddings — the retrieval operation, not the representation |
| Hybrid retrieval | Combining lexical (BM25) and vector retrieval — the dominant 2026 production pattern |
| Knowledge graph | Structured entities and relationships used to ground agent reasoning in symbolic facts |
| Semantic search | Search ranked by embedding cosine similarity rather than keyword frequency |
| Prompt caching | Reusing processed prompt segments on repeated prefixes — cache hits reportedly cost ~10% of standard input; the single largest cost lever in long sessions |
| Needle-in-a-haystack | The benchmark inserting a known fact into long context to test whether a 1M-token window is actually usable |

## Protocol & Tooling

| Term | One-Line Definition |
|---|---|
| MCP | Model Context Protocol — open JSON-RPC 2.0 standard connecting LLM hosts to external tools/data; de-facto interop standard, 10,000+ public servers (Apr 2026) |
| MCP server | A process exposing primitives (tools, prompts, resources) over MCP — the service side |
| MCP client | A connector inside an LLM host that talks to servers — the calling side; Sampling, Roots, and Elicitation are client features, not server features |
| MCP transport | The channel between client and server: stdio (local), HTTP+SSE (deprecated Mar 26, 2025), Streamable HTTP (current) |
| MCP primitive | One of the four defined capabilities: tools (functions), prompts (templates), resources (read-only data), sampling (server delegates inference to client) |
| Tool schema | The JSON Schema defining a tool's input/output — the contract the model constructs calls against |
| Capability negotiation | The MCP handshake where client and server exchange supported primitives and features |
| A2A | Agent-to-Agent protocol (Google-led) — agent↔agent communication; complements MCP (agent↔tool) |
| AGNTCY | Cisco-led framework for agent discovery, identity, and observability across org boundaries |
| AGENTS.md | Open file convention giving coding agents project instructions — read by Claude Code, Codex, Cursor; adopted by 60,000+ projects |
| Steering files | AGENTS.md / CLAUDE.md — project instructions, conventions, guardrails agents read before work |
| Skills | Packaged capability bundles (SKILL.md) loaded on demand — only the description stays in context until invoked |
| Specs | Markdown requirement/design artifacts generated before code (Kiro, Spec-Kitty) |
| Spec-driven development | Spec as the contract — agents build against it, hooks validate against it |
| Hooks | Agent-triggered validations on save/commit |
| Function calling | OpenAI's name for tool use — structured JSON args emitted by the model, executed by the host |
| CLI vs code execution | Tool-calling patterns — shell commands vs. interpreter for agent actions |

## Parallel & Isolation

| Term | One-Line Definition |
|---|---|
| Git worktree | Multiple working directories sharing one repo's object store — one per agent/branch |
| Sandboxing / filesystem isolation | Per-agent isolated directory, index, and branch |
| Sandboxed execution | Running agent-generated code in an isolated microVM/container so it cannot damage the host (Vercel Sandbox, Cloudflare Workers) |
| Port isolation | Per-worktree port offsets so parallel dev servers don't collide |
| Merge-time conflict detection | Deferring agent conflicts to git's standard merge tooling (`git merge-tree`) |
| Speculative work / ensemble agents | N agents try N approaches; best result cherry-picked |

## Evaluation & Observability

| Term | One-Line Definition |
|---|---|
| Evals | A test set plus scoring rubric used to grade an LLM/agent over time — the agent's unit-test suite |
| Success rate | Fraction of runs completing the goal — always specify granularity: step vs. plan vs. end-to-end vs. rubric-graded success; default end-to-end for executive reporting |
| Tool-call accuracy | Fraction of tool calls producing a valid, on-policy result — distinct from success rate |
| Plan validity | Fraction of generated plans that are syntactically and semantically executable |
| Verification loops / gates | Test-before, test-after — agent can't merge without passing |
| Trace | A structured log of one agent run — input, every step, every tool call, final result; the unit of debugging (LangSmith, Langfuse, Arize Phoenix) |
| Span | A single timed unit within a trace — one model call or tool call; the unit of observability |
| Eval set | A curated, versioned collection of input/expected-output pairs used to grade an agent |
| Rubric | A structured grading scale — the contract with the judge |
| Faithfulness | RAG metric: whether the answer is supported by the retrieved context |
| Context relevance | Whether the retrieved context is actually relevant to the query |
| SWE-Bench | Benchmark of 2,294 real GitHub issues testing whether an agent resolves them end-to-end; SWE-Bench Verified is the cleaned subset labs cite |
| Terminal-Bench (TBench) | Stanford benchmark of terminal-mastery tasks — the canonical eval for CLI coding agents |
| OSWorld | Benchmark of 369 real computer tasks (web, desktop, OS) for computer-use agents |
| Telemetry / observability | Tracing agent decisions, tool use, and memory updates |

## Governance & Safety

| Term | One-Line Definition |
|---|---|
| Agent control plane | The governance layer — permissions, audit, approval (talks/15) |
| Scoped permissions | Agent can only do what its task requires |
| Approval gates | Humans decide irreversible actions (sending email, modifying production data, merging, provisioning) |
| Human-in-the-loop (HITL) | A human reviews each agent decision before execution — the default risk control in regulated industries |
| Human-on-the-loop (HOTL) | A human monitors but doesn't gate every step — distinct from HITL |
| Audit trails | Machine-readable logs of every agent action (identity, timestamp, params) |
| Guardrails | Deterministic rules blocking unsafe agent actions |
| Alignment | Making AI systems reliably pursue human-intended goals — the framing under which safety work is organized |
| Prompt injection | An attack where adversarial content in retrieved data manipulates the model — ranked LLM01 in OWASP's 2025 Top 10 |
| Jailbreak | A prompt that bypasses the model's safety training — attack vector is user-side, distinct from data-side prompt injection |
| Red team | Coordinated adversarial testing for failure modes, jailbreaks, policy violations |
| Refusal | The model's ability to decline requests violating its safety policy; measured as false refusals vs. false compliances |
| Model card | Standardized documentation of a model's capabilities, limitations, training data, evals |
| System card | Documentation of a deployed AI system (model + scaffolding + controls) |
| Foundation model / GPAI | EU AI Act terms for general-purpose pre-trained models — trigger transparency and risk-assessment obligations (Articles 52-55) |
| High-risk AI system | EU AI Act Annex III category (biometric ID, hiring, credit, critical infrastructure) — triggers conformity assessment and monitoring |
| Model inventory / risk assessment | Regulated-AI artifacts — what AI exists, what it can touch |

## Training & Models

| Term | One-Line Definition |
|---|---|
| Fine-tuning | Updating model weights on a task-specific dataset after pre-training — bakes knowledge in at training time |
| Instruct tuning | Fine-tuning on instruction-response pairs to make a base model follow intent |
| RLHF | Reinforcement Learning from Human Feedback — human preference labels as reward (Ouyang et al. 2022) |
| RLAIF | Reinforcement Learning from AI Feedback — an LLM critic replaces human raters (Bai et al. 2022) |
| Constitutional AI | Anthropic's RLAIF-based pipeline where the model self-critiques against written principles |
| RL post-training | RL applied after pre-training to amplify capabilities — most commonly reasoning; behind DeepSeek-R1, o1, and most thinking models |
| MoE | Mixture of Experts — sparse subset of expert subnetworks activates per token; underlies most 2026 open-source frontier models |
| Distillation | Training a smaller student model to imitate a larger teacher — behind every Haiku-class/mini model |
| DSPy | Stanford framework for programming LLMs with composable modules and optimizers — treats prompts as compiled artifacts |

## Deployment & Economics

| Term | One-Line Definition |
|---|---|
| Cost per successful task | Total spend ÷ end-to-end successes — the metric that survives model releases and pricing shifts |
| Blended rate | Effective $/token after cache hits, batch discounts, and reserved capacity — what to use when forecasting at scale |
| Prefill / decode | Prefill: the cacheable first pass over input context; decode: the non-cacheable token-by-token output generation |
| Prefix cache / cache hit | Reusing computed attention states for a recurring input prefix — hits read at ~10% of input rate, the biggest long-context cost lever |
| Batch tier | Discounted pricing (~50%) for asynchronous requests with a 24-hour SLA — right for eval runs and background scoring |

## The Disambiguation Table — the 8 Pairs That Derail Architecture Meetings

| Term A | Term B | The Actually-Different Bit |
|---|---|---|
| **MCP** — model↔tool protocol | **A2A** — agent↔agent protocol | MCP connects a model to external tools/data; A2A connects one agent to another. Different layer, both coexist |
| **ReAct** — interleaved reasoning + tool calls, single path | **Tree of Thoughts** — multiple branching reasoning paths | ReAct is the default production loop; ToT is for problems with genuinely multiple valid solution branches |
| **RLHF** — human preference labels | **RLAIF** — AI-generated preference labels | Constitutional AI is RLAIF-based — it is not RLHF |
| **Skill** — a file on disk (SKILL.md) loaded into context on demand | **Subagent** — a spawned process with its own context window and tool budget | Skills are lightweight and cheap; subagents have independent compute cost; subagents cannot spawn subagents |
| **Agent** — perceives, acts, maintains goals, loops autonomously | **Assistant** — responds to queries in a session | An assistant does not initiate actions or persist goals without prompting |
| **Fine-tuning** — bakes knowledge into weights at training time | **RAG** — retrieves knowledge at inference time from live data | Complementary: fine-tune for style/behavior, RAG for live or frequently-updated knowledge |
| **Embeddings** — the numeric representation (model output) | **Vector search** — the retrieval operation over embeddings | You need both; neither is the other |
| **RAG** — one specific architecture: retrieve → inject → generate | **Grounding** — the broader goal of anchoring output in verifiable facts | RAG is one grounding strategy, not the only one |

## Key Signals

- Using the precise term ("retrieval budgeting", "merge-time conflict detection", "end-to-end success rate") instead of describing around it is the fluency signal interviewers pick up on
- **The disambiguation table is your strongest tool** — knowing MCP vs A2A, Skill vs subagent, RLHF vs RLAIF shows you've read primary sources, not blog summaries
- "Context engineering, not bigger windows, separates production agents from demos" — good one-liner from the 2026 playbook literature
- The 2026 frame: "The conversation moved from 'can agents work?' to 'can we govern, audit, and control them?'" (talks/15)

## Delivery Tips

- **Drop one precise term per answer**, never a list — a glossary is vocabulary, not a recitation
- When an interviewer uses a term you have here, mirror it back in your answer to confirm shared vocabulary
- If asked "what's new in AI?", anchor with the SDLC-level terms (agentic SDLC, agent control plane, context engineering) — that's the 2026 frame, not the 2023 LLM frame
- Pair a term with your proof point: "spec-driven development — that's the Kiro workflow I run" or "retrieval over context stuffing — that's my three-layer memory model"
- If an interviewer asks a model-training question (RLHF, fine-tuning), pivot to the engineering decision: "fine-tune for style and behavior, RAG for live knowledge — I use RAG because our knowledge changes weekly"

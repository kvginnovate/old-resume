# 9. Cross-Team Initiative — Spring Boot 3 Migration

**Target:** Principal Software Engineer V — The Standard (IBTE)
**Duration:** 75-85 seconds

---

## Question

**Interviewer:** "You've mentioned the AI spec-driven approach being adopted by multiple teams. But adoption across teams is different from driving a coordinated initiative. Tell me about a time you had to align multiple teams to move in the same direction."

---

## Answer

At Dish, each team had divergent Spring Boot versions. Some were on 2.4, some on 2.7, using different security scanning approaches and inconsistent CI CD practices. This caused integration issues when services needed to communicate, security vulnerabilities were being missed, and every deployment was a different process.

I proposed a platform wide Spring Boot 3 migration and establishing consistent engineering standards across all teams. But I couldn't mandate it — I didn't manage those teams.

I started by creating a migration playbook documenting every breaking change — javax to jakarta, security config changes, and all the edge cases. Then I built automated tooling using the AI spec driven approach to remediate the common patterns across 50,000 plus lines of code.

I established weekly migration office hours. Any team could drop in, ask questions, get help with their specific migration blockers. I didn't set a deadline. I let teams plan around their own sprint cycles. Instead, I published a dashboard tracking migration progress per service, and teams could see their peers making progress. That gamification helped adoption.

Within 3 months, all platform services were migrated, which was ahead of the 6 month target I had originally estimated. The automated remediation delivered a 60 percent productivity gain. Security posture improved because we standardized on Snyk scanning and same day vulnerability fixes became the norm. The practices were adopted org wide as standard.

This work was also recognized with the Annual Technical Excellence Award.

## Delivery Tips

- **"I couldn't mandate it"** — this is the key line. Sets up the whole tension. Say it plainly, not defensively
- **The dashboard + gamification detail** — this shows you understand human behavior, not just code. Most engineers skip this
- **"I let teams plan around their own sprints"** — shows maturity. You trusted teams to prioritize, and they did
- **Don't rush the result** — "3 months, ahead of the 6 month target" — let the numbers land

## Follow-Up Questions

- **"How did you handle a team that refused to migrate?"** — I didn't have one. The dashboard created peer pressure. When Team A saw Team B already migrated and shipping faster, the motivation was internal. The only pushback I got was scheduling — teams wanted to do it but needed to fit it around their feature commitments. That's why I didn't set a deadline.

- **"What was the hardest breaking change to automate?"** — The javax to jakarta namespace migration. It was a simple find-and-replace in most cases, but some libraries had transitive dependencies that still referenced javax. We had to build a dependency tree analyzer to catch those cases, and some had to wait for library updates.

- **"How did you measure the 60% productivity gain?"** — Before and after time tracking. We measured how long a typical migration task took manually — updating a Spring Security config, fixing a deprecated API, updating test dependencies. Then we measured the same task with the automated tooling. The delta was consistent across 20+ services.

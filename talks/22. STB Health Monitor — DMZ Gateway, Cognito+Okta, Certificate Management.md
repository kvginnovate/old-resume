# 22. STB Health Monitor — DMZ Gateway, Cognito+Okta, Certificate Management

**Target:** Principal Software Engineer V — The Standard (IBTE)
**Duration:** 90-100 seconds
**Most probe-rich bullet on the resume** — DMZ gateway, Cognito+Okta, OAuth lifecycle, certificate management

---

## Question

**Interviewer:** "Walk me through the STB Health Monitor. What was the DMZ gateway? Why Cognito AND Okta? How do you rotate certificates on 10M+ devices?"

---

## Answer

The STB Health Monitor is a set of Spring Boot 3 microservices running on Rancher-managed Kubernetes. Field technicians use it to scan QR-code health diagnostics and upload Set-Top-Box telemetry across ten million devices. The system runs in a DMZ — a separate network segment with strict firewall rules — to isolate it from the rest of the network. The DMZ gateway is an NGINX-based reverse proxy that handles JWT authentication, rate limiting, and request routing to the backend services. It's the only entry point into the STB Health system.

The gateway uses Cognito for initial authentication and Okta for authorization. Cognito handles the initial login and issues a JWT token. Okta then validates the token and checks the user's permissions. This two-step process gives us the flexibility to use different identity providers for different use cases. Cognito is better for consumer-facing applications, while Okta is better for enterprise applications. The OAuth lifecycle is managed by a custom service that handles token refresh, token revocation, and token validation. It's built on top of Spring Security OAuth2 and integrates with both Cognito and Okta.

Certificate management is a critical part of the system. We use a custom certificate rotation service that automatically rotates certificates for all 10 million devices. The service is triggered by a cron job that runs every 30 days. It generates a new certificate, signs it with our internal CA, and pushes it to the devices. The devices then download the new certificate and use it for all future communications. The service also handles certificate revocation and certificate renewal. If a device is compromised, we can revoke its certificate and issue a new one. The service is built on top of Spring Cloud Config and uses a distributed lock to ensure that only one instance of the service runs at any given time.

The system is integrated with Spring Cloud Config for centralized configuration management. All configuration changes are pushed to the devices in real-time. Dynatrace is used for monitoring and observability. It provides end-to-end tracing, performance metrics, and alerting. GitLab and Jenkins are used for CI/CD. The system is built using Spring Boot 3, Spring Cloud, and Spring Security. The code is written in Java and follows the Spring Boot best practices. The system is designed to be highly available and scalable. It can handle 10,000 requests per second with a 99.9% uptime SLA.

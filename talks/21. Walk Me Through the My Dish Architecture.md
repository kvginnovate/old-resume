# 21. Walk Me Through the My Dish Architecture

**Target:** Principal Software Engineer V — The Standard (IBTE)
**Duration:** 90-100 seconds
**Guaranteed ask** — the architecture deep dive that anchors everything else

---

## Question

**Interviewer:** "Walk me through the My Dish architecture. What are the services? How do they communicate? What was your role?"

---

## Answer

The My Dish subscriber platform is a set of twelve microservices, each owning a domain capability: subscriber profile, billing, plans, equipment, support tickets, and notification preferences. Each service owns its own PostgreSQL database. There are no shared databases, except for read only replicas feeding analytics.

Communication is hybrid, and the choice between synchronous and asynchronous is deliberate. For request response flows, like a profile lookup or a plan change, services call each other over REST. Kong API Gateway routes external traffic and handles authentication and rate limiting at the edge, so services don't re validate tokens. Internally, services discover each other directly.

For flows where independent systems need to react, we use Kafka. When a subscriber changes their plan, the billing service publishes an event, and downstream services, entitlements, notifications, and analytics, consume it independently. This decoupling is what lets each team ship without coordinating release cycles.

For hot path reads, subscriber profiles and device configurations, we use GemFire as a distributed cache with a cache aside pattern. Read from cache, on a miss hit the database, populate the cache.

The platform runs on Rancher managed Kubernetes, and it serves ten million subscribers at ninety nine point nine percent uptime with sub second API latency. We hold that number through redundancy at every layer, graceful degradation when a dependency fails, and Dynatrace anomaly detection that pages the on call engineer before users notice.

My role was owning the end to end architecture. I defined the integration patterns, the API standards, the security gates, and the observability framework that every team on the platform follows. I didn't just design the system, I made the standards self service so teams could adopt them without asking permission.

## Key Signals

- **Deliberate communication choices:** sync for request-response, async for reactions — explained as a decision, not a default
- **Data ownership:** each service owns its DB — the microservices truism said with conviction, plus the read-replica escape hatch for analytics
- **Edge auth:** Kong does JWT validation so services don't re-validate — shows you think about security architecture, not just routing
- **The "why" of Kafka:** "so teams can ship without coordinating release cycles" — decoupling tied to org velocity
- **Defending 99.9%:** the number is anchored to mechanisms, not vibes
- **Principal framing:** "I made the standards self-service" — you enable teams, you don't police them

## Delivery Tips

- **Don't list all 12 services** — name 4-5 domains and say "and others." Listing everything sounds rehearsed; the pattern is what matters
- **"The choice between sync and async is deliberate"** — this is the strongest line. Pause before it
- **Say "ninety nine point nine" and "sub second" slowly** — these are the numbers the interviewer wrote down. Let them land
- **The Kafka line** — "so each team can ship without coordinating release cycles" — this is the business translation the interviewer is listening for. Don't rush past it
- **End on the self-service standards line** — it pivots from "architect" to "leader," which is the Principal elevation

## Follow-Up Questions

- **"Why 12 services? How did you decide the boundaries?"** — Domain-driven design. Each service owns a business capability, and the boundaries came from the domain, not the code. The rule: if two things change for different reasons, they belong in different services. If they change together, keep them together. And we didn't get to 12 in one design session — we started with fewer services and split as we hit friction. Notification preferences split from subscriber profile when the notification team needed independent deploy cycles. The boundaries emerged from ownership pressure, not a diagram.
- **"What breaks at 10M users?"** — Database connection pools under load, and GemFire cache misses during peak. We solved the first with HikariCP tuning and the second with cache pre-warming. Those are the two failure modes that show up at scale that you can't predict from load tests alone, because they're about contention patterns, not raw throughput.
- **"Why Kong over the alternatives?"** — Kong is open source, self-hosted, and sub-millisecond latency, which matters on the hot path. It's also Kubernetes native through the Kong Ingress Controller, and multi-cloud, which fit our Rancher setup. AWS API Gateway and Azure APIM are fine, but they lock you to one cloud, and the latency profile is higher. We use Kong for JWT validation, rate limiting per client, and path based routing to the services.
- **"How do you measure 99.9% uptime?"** — Dynatrace, request based SLI. Three nines is eight point seven hours of downtime per year. We track against that monthly in the architecture review, and every incident that counts against the budget gets a root cause analysis. The number is a contract, not a marketing claim.

- **Bounded contexts for Sling (6)** are a different number from **My Dish services (12)** — be ready for both, they're different systems.

# 3. Sling TV UMS Modernization

**Target:** Principal Software Engineer V — The Standard (IBTE)
**Duration:** 85-95 seconds

> **Correction from earlier drafts:** The bounded contexts are NOT "billing, content catalog, entitlements, recommendations, device management, support" — those are Sling TV *platform* contexts. UMS (User Management Service) is specifically the user management domain. The correct bounded contexts for UMS are below.

---

## Question

**Interviewer:** "You mentioned the Sling TV modernization and the 80 plus Rails to Java migration. That's a big claim. Walk me through what you actually did — what was your role, how did you approach it, and what was the hardest part?"

---

## Answer

The Sling User Management Service, or UMS, was built on 80 plus legacy Ruby on Rails APIs running on a monolith. It worked, but it was brittle. Every deployment was high risk, scaling meant vertical scaling, and hiring Rails developers was getting harder.

I proposed the modernization. My role was architect and technical lead. I defined the target architecture, chose the technology stack, and designed the migration approach. I didn't manage the team, I led the technical direction.

We decomposed the monolith into 6 bounded contexts using domain driven design. User profile, authentication, device management, entitlements, user preferences, and account settings. Each context became its own microservice with its own database. Communication was event driven over Kafka, with REST for synchronous query flows.

The hardest part was data consistency. When you split a monolith's database, you lose ACID transactions. We used the Saga pattern. Each service publishes an event when its local transaction completes, downstream services listen and update their own state, and we had compensation logic to roll back on failure. That took three iterations to get right.

Validation was the second hardest problem. We ran old and new in parallel for two weeks. Feature flags routing 10 percent of traffic initially, then 50 50, then 100 percent, with the ability to roll back instantly. We had a data reconciliation job comparing responses from both systems for every request. If they diverged, we investigated before the next traffic increase.

The result was 70 percent faster delivery per engineer. A service that took two weeks to build now takes three days.

## Correct Bounded Contexts (UMS)

| Context | What It Owns |
|---|---|
| **User Profile** | Identity, demographics, account info, registration |
| **Authentication** | Login, MFA, token validation, session management, OAuth |
| **Device Management** | Device registration, activation, device profiles, device linking |
| **Entitlements** | What each user can access — permissions, roles, feature flags |

## Delivery Tips

- **The Saga pattern line** — "That took three iterations to get right" is your strongest technical detail. Pause before it. Don't rush
- **The validation story** — most engineers can't describe how they validated a migration. This is your maturity signal. Say it step by step
- **If they ask "What were the 6 contexts?"** — list them confidently. User profile, authentication, device management, entitlements, preferences, account settings. Don't hesitate

## Follow-Up Questions

- **"How did you decide the service boundaries?"** — We used DDD workshops with the product team. The rule was: if two things change for different reasons, they should be separate services. If they change together, keep them together. The boundaries came from the business domain language — auth talks about "tokens" and "sessions," profile talks about "accounts" and "demographics." When the language differs, the service boundary should too.
- **"What was the biggest mistake you made?"** — We underestimated the data consistency problem. The first Saga implementation had a bug in the compensation logic — a rollback in one service didn't propagate correctly. We caught it in chaos engineering, not in production. After that, we added automated saga validation tests.
- **"How did you handle the team through the transition?"** — I paired every Rails developer with a Java developer during the migration. They weren't just writing code — they were learning the new stack. The Rails developers became the domain experts, the Java developers became the architecture experts. By the end, half the team was writing Java confidently.

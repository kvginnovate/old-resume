# Kafka Event-Driven Architecture for Sling TV

## Question

**Interviewer:** "You mentioned Kafka and event-driven architecture in the UMS modernization. Walk me through how you designed the event-driven architecture for Sling TV."

## Full Answer

When I designed the event driven architecture for the Sling TV UMS migration, the legacy system had 80 plus Ruby on Rails APIs that were tightly coupled with synchronous REST calls. A failure in any downstream service would cascade across the whole system.

My design approach had four steps.

First, I identified event boundaries. I mapped every synchronous call between services and asked, does this caller need an immediate response, or is it just notifying? Authentication and content authorization needed immediate responses, so we kept those as REST. Billing, notifications, analytics, and recommendations did not need immediate responses, so we moved those to Kafka events.

Second, I defined event contracts. Every event had a standard structure — an event ID, an event type, a timestamp, and the data payload. For example, a subscription created event had the subscriber ID, plan ID, start date, and the channel. This consistency meant any consumer could process any event without knowing the producer's internals.

Third, I chose partition keys for ordering. I used subscriber ID as the Kafka message key. This guaranteed that all events for the same subscriber go to the same partition, which means billing always sees subscription created before subscription upgraded for the same customer. That ordering was critical for correctness.

Fourth, I set topic configurations. We had a replication factor of 3 so we could tolerate a broker failure. We had 12 partitions per topic, matching our consumer scaling target. Retention was 7 days for operational topics and 30 days for audit topics.

For consumer patterns, each downstream service had its own consumer group so they could scale independently. We had a dead letter queue for messages that failed processing after 3 retries with exponential backoff. And every consumer was idempotent — we used the event ID to prevent duplicate processing if a consumer crashed and restarted.

The result was a decoupled system where each service could scale independently, failure in one service didn't cascade, and we had full event replay capability for debugging production issues.

## Key Principles

- Event boundaries: keep REST for immediate responses, Kafka for async notifications
- Partition key = subscriber ID preserves ordering per customer
- Each consumer group scales independently
- Idempotent consumers prevent duplicate processing
- DLQ for failed messages after 3 retries with exponential backoff
- Replication factor 3, 12 partitions per topic
